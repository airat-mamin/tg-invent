# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## Разработка Telegram-бота для инвентаризации ИТ-оборудования по фото шильдиков (наклеек)

**Версия:** 2.0
**Статус:** к реализации

---

## 1. Общие сведения

* **Наименование системы:** IT-Asset-OCR-Bot
* **Назначение:** Автоматизация сбора серийных номеров, сервисных тегов и моделей мониторов/ПК по фотографиям заводских наклеек (шильдиков) с сохранением результатов в базу данных и выгрузкой для последующей инвентаризации.
* **Цели:**
  1. Сократить время внесения одной единицы оборудования в учёт до 10–15 секунд.
  2. Исключить ошибки ручного ввода серийных номеров.
  3. Обеспечить накопление данных в машиночитаемом виде (не только копирование значений вручную).
* **Целевая аудитория:** Системные администраторы, инженеры технической поддержки, сотрудники склада.
* **Режим работы:** Внутренний инструмент организации, развёртывание в локальном контуре, доступ только для сотрудников из списка разрешённых.

### 1.1. Термины и сокращения

| Термин | Значение |
| --- | --- |
| Шильдик | Заводская наклейка на корпусе оборудования с моделью, серийным номером и штрихкодами |
| S/N | Serial Number, серийный номер |
| Service Tag | Сервисный тег Dell — 7-символьный идентификатор |
| Контур | Независимый метод извлечения данных из изображения (см. п. 2.2) |
| VLM | Vision Language Model, мультимодальная нейросеть (Llama 3.2 Vision) |
| Карточка | Результат распознавания одной наклейки: brand, model, serial_number, service_tag |

---

## 2. Функциональные требования

### 2.1. Интерфейс взаимодействия

Взаимодействие осуществляется через мессенджер Telegram.

**Принимаемые типы сообщений:**

1. **Изображение (Photo)** — одиночная фотография наклейки напрямую со смартфона (сжатая Telegram).
2. **Документ (Document)** — фотография, отправленная без сжатия, MIME-типы `image/jpeg`, `image/png`, `image/heic`, `image/webp`.
3. **Медиагруппа (альбом)** — несколько фотографий одним сообщением; обрабатывается каждое изображение по очереди, ответ присылается на каждое отдельным сообщением.

**Команды бота:**

| Команда | Назначение |
| --- | --- |
| `/start` | Приветствие и краткая инструкция: «Отправьте мне чёткое фото наклейки на мониторе/ПК, и я пришлю вам данные для копирования» |
| `/help` | Рекомендации по съёмке: наклейка целиком в кадре, без бликов и наклона, фокус наведён, при мелком шрифте — отправлять файлом без сжатия |
| `/last` | Показать последние 10 сканирований текущего пользователя |
| `/export` | Выгрузить сканирования в файл CSV/XLSX (см. п. 2.7) |
| `/stats` | Статистика: количество сканирований, распределение по контурам, доля неудач (доступна администраторам) |
| `/parts` | Накопленные соответствия «номер детали → модель» фрагментом YAML для переноса в шаблон (доступна администраторам) |
| `/cancel` | Прервать текущий диалог ручной корректировки |

### 2.2. Логика обработки и распознавания (трёхконтурная схема)

Бот использует каскадную схему: каждый следующий контур запускается **только** если предыдущий не дал валидного результата. Это исключает избыточную нагрузку на CPU/GPU.

```
                 [Пользователь отправляет фото]
                               │
                               ▼
                  [Предобработка: OpenCV]
                               │
                               ▼
              ┌────────────────────────────────┐
              │ Контур 0: Штрихкоды / QR / DM  │  pyzbar, zxing-cpp
              └───────────────┬────────────────┘
                              │
              Найден валидный S/N или Service Tag?
                              ├───► ДА ──────────────────┐
                              ▼ НЕТ                      │
              ┌────────────────────────────────┐         │
              │ Контур 1: EasyOCR + RegEx      │         │
              └───────────────┬────────────────┘         │
                              │                          │
              Распарсены ключевые поля?                   │
                              ├───► ДА ──────────────────┤
                              ▼ НЕТ                      │
              ┌────────────────────────────────┐         │
              │ Контур 2: Llama 3.2 Vision     │  Ollama │
              └───────────────┬────────────────┘         │
                              │                          │
                              ▼                          ▼
                      [Нормализация и валидация значений]
                                       │
                                       ▼
                     [Вывод карточки + подтверждение]
                                       │
                                       ▼
                               [Запись в БД]
```

**Критерий успеха контура (единый для всех контуров):** извлечён хотя бы один идентификатор — `serial_number` **или** `service_tag` — прошедший валидацию по п. 2.4. Поля `brand` и `model` являются желательными, но их отсутствие **не** является основанием для перехода к следующему контуру.

**Обогащение результата:** если контур дал идентификатор, но не дал `brand`/`model`, эти поля дополняются из результатов работы предыдущих контуров (например, штрихкод дал S/N, а OCR-текст дал модель) без запуска следующего контура.

#### 2.2.0. Контур №0: Распознавание штрихкодов

* На шильдиках ИТ-оборудования серийный номер и Service Tag в подавляющем большинстве случаев продублированы штрихкодом (Code128, Code39) или двумерным кодом (QR, DataMatrix).
* Библиотеки: `pyzbar` (Code128/Code39/QR) и `zxing-cpp` либо `cv2.barcode` (DataMatrix, устойчивее к наклону).
* Декодирование выполняется на исходном изображении и на предобработанных вариантах (см. п. 2.3): в оттенках серого, с повышенным контрастом, с поворотами на 90/180/270°.
* Из декодированных строк идентификаторы извлекаются по правилам:
  * строка длиной ровно 7 символов из алфавита `[A-Z0-9]` рядом с текстовой меткой Service Tag → `service_tag`;
  * строка длиной 5–30 символов из алфавита `[A-Z0-9-]` → кандидат в `serial_number`;
  * при нескольких кандидатах приоритет отдаётся штрихкоду, ближайшему к текстовой метке `S/N` (по координатам bbox, метки берутся из результата Контура №1, если он уже был выполнен, иначе — по порядку сверху вниз).
* Точность метода близка к 100%, время работы — десятки миллисекунд, поэтому контур выполняется первым.

#### 2.2.1. Контур №1: Легковесный локальный OCR (EasyOCR)

* Библиотека `easyocr` (языки `en`; `ru` подключается опционально и увеличивает время инициализации) в связке с `opencv-python` для предобработки (см. п. 2.3).
* Модель EasyOCR загружается в память **однократно при старте приложения**, а не на каждый запрос.
* Вызов OCR выполняется в отдельном пуле потоков (`asyncio.to_thread` / `run_in_executor`), чтобы не блокировать event loop aiogram.
* Из результата (список блоков `текст + bbox + confidence`) значения извлекаются регулярными выражениями по **склеенному тексту**, а при неудаче — по **соседству bbox**: если найден блок с меткой (`S/N`, `Service Tag`), значение ищется в блоке справа или снизу от него в пределах 1.5 высоты строки.

**Регулярные выражения (регистронезависимые, применяются к тексту, приведённому к верхнему регистру):**

```
Service Tag:   (?:SERVICE\s*TAG|SERVICE\s*CODE|\bS[\/\\.]?T\b)\s*[:.#№]?\s*([A-Z0-9]{7})\b
Serial Number: (?:S[\/\\.\s]?N|SERIAL\s*(?:NO\.?|NUMBER|NUM)?)\s*[:.#№]?\s*([A-Z0-9][A-Z0-9\-]{4,29})\b
Модель:        (?:MODEL(?:\s*(?:NO\.?|NAME))?|MODEL:|MDL)\s*[:.#№]?\s*([A-Z0-9][A-Z0-9\-\/ ]{2,24})\b
Производитель: поиск по словарю брендов (DELL, HP, HEWLETT-PACKARD, LENOVO, SAMSUNG, LG,
               ACER, ASUS, PHILIPS, AOC, BENQ, VIEWSONIC, IIYAMA, NEC, EIZO, HUAWEI, XIAOMI,
               MSI, GIGABYTE, DEXP, IRBIS) с нечётким сравнением (Левенштейн, порог ≤ 1)
```

Требования к шаблонам:

* метка и значение могут быть разделены переводом строки — при склейке текста переводы строк заменяются пробелом, дополнительно выполняется поиск с `\n` между меткой и значением;
* учитываются варианты написания с кириллическими омоглифами (`С/N`, `Ѕ/N`) — перед матчингом выполняется транслитерация кириллических букв `А В Е К М Н О Р С Т У Х` в латинские аналоги;
* **исключаются** ложные срабатывания: значения, совпавшие с MAC-адресом (`([0-9A-F]{2}[:-]){5}[0-9A-F]{2}`), номером партии (`P/N`, `PART NO`), кодом регулятора (`FCC ID`, `EAC`, `CE`), датой производства и напряжением питания.

#### 2.2.2. Контур №2: Локальная нейросеть (Llama 3.2 Vision)

* Запускается, если Контур №0 и Контур №1 не дали валидного идентификатора.
* Изображение передаётся на локальный сервер Ollama через `ollama.AsyncClient`.
* **Модель:** `llama3.2-vision:11b` (в квантованном виде требует ~8–10 ГБ VRAM). Вариант «3b» из версии 1.0 ТЗ исключён: модели Llama 3.2 Vision выпускаются только в размерах 11B и 90B, а 3B — текстовая модель без поддержки изображений.
* Параметры генерации: `temperature=0`, `format="json"`, ограничение по числу токенов ответа.
* Системный промпт:

  > «Ты — ассистент системного администратора. Твоя задача — внимательно изучить изображение наклейки ИТ-оборудования. Найди и извлеки следующие параметры: Производитель (Brand), Модель (Model), Серийный номер (S/N или Serial Number), Сервисный тег (Service Tag, только для Dell). Верни ответ СТРОГО в формате JSON с ключами: brand, model, serial_number, service_tag. Если поле не найдено, укажи null. Никакого лишнего текста в ответе быть не должно.»

* **Ожидаемая схема ответа:**

```json
{
  "brand": "Dell",
  "model": "E2722H",
  "serial_number": "CN0Y71R3TV20019B13QT",
  "service_tag": "9YSCSF3"
}
```

* **Обработка ответа модели:**
  * ответ парсится как JSON; если модель обрамила его тройными обратными кавычками или добавила пояснения, выполняется извлечение первого JSON-объекта по фигурным скобкам;
  * при невалидном JSON выполняется **одна** повторная попытка с уточняющей инструкцией «Верни только JSON-объект»;
  * при повторной неудаче пользователю выдаётся сообщение об ошибке распознавания с рекомендациями по пересъёмке;
  * строковые значения `"null"`, `"none"`, `"n/a"`, `"-"`, пустые строки приводятся к `null`;
  * значения проходят ту же нормализацию и валидацию, что и в остальных контурах (п. 2.4). Галлюцинация модели, не прошедшая валидацию формата, отбрасывается.
* **Таймаут** на запрос — конфигурируемый, по умолчанию 60 с. По истечении — сообщение об ошибке, запись в лог.
* **Ограничение параллелизма:** одновременно к Ollama выполняется не более `MAX_CONCURRENT_VLM` запросов (по умолчанию 1), остальные ставятся в очередь; пользователю при постановке в очередь отправляется сообщение «Распознаю изображение…».

### 2.3. Предобработка изображений (OpenCV)

Выполняется однократно, результаты переиспользуются всеми контурами:

1. Приведение к оттенкам серого.
2. Масштабирование: если меньшая сторона < 1000 px — увеличение (`INTER_CUBIC`); если большая сторона > 2500 px — уменьшение для ускорения OCR.
3. Повышение контраста методом CLAHE.
4. Подавление шума (`fastNlMeansDenoising`) и адаптивная бинаризация (`adaptiveThreshold`) — отдельный вариант изображения для OCR и штрихкодов.
5. Автоповорот: определение угла наклона текста и выравнивание (`deskew`).

В контуры №0 и №1 передаётся набор вариантов изображения; используется первый, давший валидный результат. В Контур №2 передаётся **исходное** (не бинаризованное) изображение — VLM работает лучше на естественных изображениях.

### 2.4. Нормализация и валидация извлечённых значений

**Нормализация (применяется ко всем контурам):**

* приведение к верхнему регистру;
* удаление пробелов внутри идентификаторов и обрезка служебных символов по краям (`:`, `.`, `#`, `*`, `|`);
* транслитерация кириллических омоглифов в латиницу.

**Валидация формата:**

| Поле | Правило |
| --- | --- |
| `service_tag` | Ровно 7 символов, алфавит `[A-Z0-9]` |
| `serial_number` | 5–30 символов, алфавит `[A-Z0-9-]`, содержит минимум одну цифру |
| `model` | 2–25 символов, не совпадает с названием бренда |
| `brand` | Присутствует в словаре брендов (после нечёткого сопоставления) |

**Два представления серийного номера.** Идентификатор хранится и показывается в двух видах:

* `serial_number` — машинный вид без дефисов, ровно как в штрихкоде. Используется для копирования, дедупликации, поиска и передачи в учётные системы.
* `serial_display` — вид «как напечатано на наклейке», с разбивкой на группы (`CN-0Y71R3-TV200-19B-13QT-A01`). Служит для визуальной сверки пользователем.

Дефисы в PPID Dell являются только разделителем групп, поэтому убираются при канонизации; у прочих производителей дефис может быть частью номера и сохраняется. Разбивка на группы берётся из прочитанного OCR текста, если он сходится с машинным видом, иначе рассчитывается по формату PPID.

**Определение модели по номеру детали.** У ряда производителей номер детали зашит в серийный номер (у Dell `CN-07MT01-QDC00-74Q-0DDS-A04` → `07MT01`) и одинаков у одинаковых устройств. Если сам текст модели на снимке не прочитан, она подставляется по накопленному соответствию «номер детали → модель». Источники в порядке приоритета: ручные исправления пользователя, значения, прочитанные с наклейки и подтверждённые пользователем, значения из шаблона производителя. Подставленная модель помечается в карточке как определённая по номеру детали и подлежит подтверждению: она получена не с этого снимка.

**Работа с неоднозначными символами:** если значение **не прошло** валидацию, выполняется подбор вариантов с заменой визуально схожих символов (`O↔0`, `I↔1`, `l↔1`, `B↔8`, `S↔5`, `Z↔2`, `G↔6`, `Q↔0`). Прошедшее валидацию значение помечается флагом «скорректировано» и **обязательно** выносится на подтверждение пользователю. Автоматическая замена символов в значениях, уже прошедших валидацию, **запрещена**.

Каждой карточке присваивается признак источника (`barcode` / `ocr` / `vlm`) и уровень доверия:

* `high` — Контур №0 либо Контур №1 с confidence OCR ≥ 0.8 без коррекции символов;
* `medium` — Контур №1 с coррекцией символов или confidence < 0.8;
* `low` — Контур №2.

### 2.5. Требования к выводу информации

Ответ формируется в `parse_mode=HTML` (HTML выбран вместо MarkdownV2, чтобы избежать ошибок экранирования спецсимволов в серийных номерах). Значения полей оборачиваются в тег `<code>` — в клиентах Telegram такое значение копируется в буфер обмена одним нажатием.

**Пример сообщения:**

```
🖥 Оборудование распознано (штрихкод)

• Производитель: DELL
• Модель: E2722H
• Серийный номер: CN-0Y71R3-TV200-19B-13QT-A01
• Service Tag: 84ZCSF3

Нажмите на значение, чтобы скопировать его как есть.
Кнопка ниже копирует серийный номер без дефисов.
```

Дополнительно:

* серийный номер выводится в виде «как напечатано» (п. 2.4): сплошную строку из штрихкода тяжело сверять с наклейкой посимвольно;
* поскольку нажатие на моноширинное значение копирует ровно показанный текст, машинный вид выносится в инлайн-кнопку `copy_text` (Bot API 7.11+), которая копирует номер без дефисов;
* в заголовке указывается источник распознавания (`штрихкод` / `OCR` / `нейросеть`);
* при уровне доверия `medium` или `low` добавляется предупреждение: «⚠️ Проверьте значения — распознавание могло быть неточным»;
* отсутствующие поля не выводятся вовсе (вместо вывода `null`);
* если не найдено ни одного идентификатора, отправляется сообщение о неудаче с рекомендациями по пересъёмке из `/help`.

### 2.6. Подтверждение и ручная корректировка

Под карточкой размещается инлайн-клавиатура:

| Кнопка | Действие |
| --- | --- |
| ✅ Верно | Карточка сохраняется в БД со статусом `confirmed`, клавиатура убирается |
| ✏️ Исправить | Запуск FSM-диалога: бот последовательно предлагает изменить поля, введённые значения проходят валидацию, результат сохраняется со статусом `corrected` |
| 🔄 Переснять | Карточка отбрасывается (статус `discarded`), выводится напоминание о правилах съёмки |

Карточки, не подтверждённые в течение сессии, сохраняются со статусом `pending` и в выгрузку по умолчанию не попадают.

### 2.7. Хранение данных и выгрузка

**СУБД:** SQLite (файл в примонтированном томе). Доступ через `aiosqlite`, схема создаётся миграциями при старте.

**Таблица `scans`:**

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | INTEGER PK | Идентификатор записи |
| `created_at` | TEXT (ISO-8601) | Время сканирования (UTC) |
| `tg_user_id` | INTEGER | Telegram ID пользователя |
| `tg_username` | TEXT | Имя пользователя на момент сканирования |
| `brand` | TEXT NULL | Производитель |
| `model` | TEXT NULL | Модель |
| `serial_number` | TEXT NULL | Серийный номер, машинный вид без дефисов |
| `serial_display` | TEXT NULL | Серийный номер в виде «как напечатано на наклейке» |
| `service_tag` | TEXT NULL | Сервисный тег |
| `source` | TEXT | `barcode` / `ocr` / `vlm` |
| `confidence` | TEXT | `high` / `medium` / `low` |
| `status` | TEXT | `pending` / `confirmed` / `corrected` / `discarded` |
| `raw_text` | TEXT NULL | Сырой текст OCR либо ответ VLM (для разбора ошибок) |
| `image_path` | TEXT NULL | Путь к сохранённому изображению (если включено хранение) |
| `duration_ms` | INTEGER | Длительность обработки |
| `location` | TEXT NULL | Кабинет/площадка (заполняется пользователем, опционально) |

**Индексы:** по `serial_number`, `service_tag`, `tg_user_id`, `created_at`.

**Дедупликация:** при сохранении выполняется поиск записи с тем же `serial_number` или `service_tag` в статусе `confirmed`/`corrected`. При совпадении пользователю выводится предупреждение «Это оборудование уже сканировалось <дата> пользователем <имя>» с выбором «Сохранить повторно» / «Отменить».

**Выгрузка (`/export`):** файл CSV (UTF-8 с BOM для корректного открытия в Excel) и XLSX со всеми подтверждёнными записями; оба представления серийного номера выводятся отдельными колонками. Поддерживаются параметры: `/export today`, `/export week`, `/export all`. Обычный пользователь выгружает только свои записи, администратор — все.

### 2.8. Контроль доступа

* Список разрешённых Telegram ID задаётся в конфигурации (`ALLOWED_USER_IDS`), отдельно задаётся список администраторов (`ADMIN_USER_IDS`).
* Все апдейты от пользователей вне списка отклоняются на уровне middleware aiogram с сообщением «Доступ ограничен. Обратитесь к администратору» и записью попытки в лог.
* Требование обязательно: бот использует локальный GPU, и открытый доступ означает бесконтрольное потребление ресурсов посторонними.
* Антифлуд: не более `RATE_LIMIT_PER_MINUTE` (по умолчанию 10) изображений в минуту от одного пользователя; при превышении — вежливый отказ без запуска обработки.

### 2.9. Обработка ошибок и негативные сценарии

| Ситуация | Поведение системы |
| --- | --- |
| Прислан не поддерживаемый тип (видео, стикер, голос, текст) | Подсказка с указанием, что нужно прислать фото |
| Файл больше 20 МБ | Сообщение о лимите Bot API на скачивание с просьбой прислать сжатое фото |
| Не удалось скачать файл из Telegram | 3 повторные попытки с экспоненциальной задержкой, затем сообщение об ошибке |
| Изображение повреждено / не декодируется | Сообщение «Не удалось открыть изображение» |
| Ни один контур не нашёл идентификатор | Сообщение о неудаче + рекомендации по съёмке + запись в БД со статусом `discarded` для анализа |
| Сервер Ollama недоступен | Пользователю сообщается, что углублённое распознавание временно недоступно и выдаётся частичный результат OCR (при наличии); ошибка пишется в лог; периодический health-check |
| Таймаут Ollama | Сообщение «Распознавание заняло слишком много времени, попробуйте отправить фото без сжатия» |
| VLM вернула невалидный JSON | 1 повторная попытка, затем сообщение об ошибке (п. 2.2.2) |
| Исключение в обработчике | Глобальный error-handler aiogram: пользователю — нейтральное сообщение, в лог — полный traceback; бот продолжает работу |

## 3. Нефункциональные требования

### 3.1. Производительность и целевое время ответа

| Контур | Целевое время (95-й перцентиль) |
| --- | --- |
| Контур №0 (штрихкод) | ≤ 1 с |
| Контур №1 (EasyOCR) | ≤ 5 с |
| Контур №2 (VLM на GPU) | ≤ 30 с |

Время измеряется от получения сообщения ботом до отправки карточки.

### 3.2. Требования к аппаратному обеспечению

* CPU: 4 ядра и более.
* RAM: не менее 16 ГБ.
* **GPU: обязателен для Контура №2** — не менее 10 ГБ VRAM (NVIDIA, CUDA). На CPU время ответа `llama3.2-vision:11b` составляет десятки секунд и делает контур практически неприменимым.
* Диск: 30 ГБ (модели Ollama + модели EasyOCR + БД + изображения).
* При отсутствии GPU система должна корректно работать в режиме «только контуры №0 и №1» (управляется флагом конфигурации `VLM_ENABLED`).

### 3.3. Конкурентность

* Бот обрабатывает параллельные запросы от разных пользователей без блокировки event loop: все тяжёлые вызовы (OCR, декодирование изображений) выносятся в пул потоков, обращения к Ollama сериализуются семафором.
* Целевая нагрузка: до 10 одновременно работающих пользователей, до 500 сканирований в день.

### 3.4. Надёжность и наблюдаемость

* Структурированное логирование (JSON) с уровнями; в лог пишутся: идентификатор пользователя, выбранный контур, длительность, результат, ошибки.
* Логи ротируются, срок хранения — 30 дней.
* Health-check эндпоинт или периодическая проверка доступности Ollama при старте и раз в 5 минут.
* Автоматический перезапуск сервиса при падении (`restart: unless-stopped` в Docker Compose).

### 3.5. Безопасность и приватность

* Токен бота и прочие секреты хранятся в `.env`, файл добавлен в `.gitignore` и **не** попадает в репозиторий. В репозитории присутствует `.env.example`.
* Хранение исходных изображений отключаемо (`STORE_IMAGES`), при включении задаётся срок автоматического удаления (`IMAGE_RETENTION_DAYS`, по умолчанию 30).
* Все данные обрабатываются локально; передача изображений во внешние облачные сервисы **запрещена**.
* Доступ к БД и каталогу изображений ограничен пользователем сервиса.

## 5. Критерии приёмки

### 5.1. Тестовый набор

Формируется набор из **не менее 100 реальных фотографий** шильдиков, снятых на смартфоны, с размеченными эталонными значениями (`brand`, `model`, `serial_number`, `service_tag`). Набор должен включать:

* не менее 5 разных производителей;
* фотографии со штрихкодом и без;
* заведомо сложные случаи: блики, наклон, частичная засветка, мелкий шрифт, потёртая наклейка (не менее 20% выборки).

Сбор и разметка набора — отдельная задача этапа 1, без неё приёмка невозможна.

### 5.2. Метрики

| Показатель | Целевое значение |
| --- | --- |
| Точность `serial_number` (полное совпадение строки) на фотографиях приемлемого качества | ≥ 95% |
| Точность `service_tag` на оборудовании Dell | ≥ 97% |
| Доля запросов, закрытых Контуром №0 | измеряется, служит основанием для решения о целесообразности Контура №1 |
| Доля ложных значений (выдано неверное значение вместо отказа) | ≤ 2% |
| Доля отказов на фотографиях приемлемого качества | ≤ 5% |
| Время ответа | соответствует п. 3.1 |

**Отдельное проектное решение по итогам этапа 3:** если Контур №0 закрывает большую часть запросов, а остаток всё равно уходит в Контур №2, целесообразность Контура №1 пересматривается — EasyOCR тянет за собой `torch`, существенно увеличивая размер образа и время старта. Решение принимается по замеренной доле срабатываний каждого контура.

### 5.3. Прочие условия приёмки

* Проект собирается и запускается командой `docker compose up` на чистой машине по инструкции из `readme`.
* Все негативные сценарии из п. 2.9 воспроизведены и обработаны без падения бота.
* Покрытие тестами модулей нормализации, валидации и парсинга ответа VLM.
* Линтеры (`ruff`, `black --check`, `mypy`) проходят без ошибок.

## 8. Изменения относительно версии 1.0

| № | Изменение | Причина |
| --- | --- | --- |
| 1 | Добавлен Контур №0 (штрихкоды/QR/DataMatrix) перед OCR | На большинстве шильдиков идентификаторы продублированы штрихкодом; точность близка к 100% против ошибок OCR на символах `0/O`, `1/I`, `8/B` |
| 2 | Уточнён критерий перехода между контурами | В версии 1.0 требовалось найти «Модель и Серийный номер», при этом regex для модели отсутствовал — условие было невыполнимым |
| 3 | Расширены регулярные выражения, добавлен поиск по соседству bbox, фильтрация ложных срабатываний (MAC, P/N, FCC ID) | Исходные шаблоны не работали при написании `SERIAL NO`, `SN`, переносе строки между меткой и значением, кириллических омоглифах |
| 4 | Исключён вариант модели `llama3.2-vision:3b`, зафиксирована `11b` | Модели Llama 3.2 Vision существуют только в размерах 11B и 90B |
| 5 | Добавлены требования к аппаратному обеспечению (GPU ≥ 10 ГБ VRAM) и целевое время ответа | Без GPU Контур №2 неприменим по времени отклика |
| 6 | Указан `parse_mode=HTML` и обёртка значений в `<code>` | Обещанное копирование по нажатию работает только для моноширинных сущностей Telegram |
| 7 | Добавлены нормализация, валидация, уровни доверия и подтверждение пользователем | Ошибка в одном символе серийного номера обесценивает запись, а обнаруживается уже в учётной системе |
| 8 | БД переведена из «опционально» в обязательные требования, добавлены дедупликация и экспорт | Назначение системы — инвентаризация; без хранения и выгрузки цель не достигается |
| 9 | Добавлен контроль доступа и антифлуд | Открытый бот означает бесконтрольное использование локального GPU посторонними |
| 10 | Добавлены раздел обработки ошибок, требования к конкурентности (пул потоков, семафор к Ollama) | Блокирующие вызовы EasyOCR и Ollama в асинхронном боте приводят к остановке обработки прочих сообщений |
| 11 | Добавлены критерии приёмки, тестовый набор фотографий и метрики | Без измеримых критериев приёмка невозможна |
| 12 | Добавлены требования к развёртыванию, конфигурации, логированию, приватности | Отсутствовали в версии 1.0 |
| 13 | Введены два представления серийного номера: машинное и «как напечатано», оба хранятся и выгружаются | Сплошную строку из штрихкода невозможно посимвольно сверить с наклейкой, а в учётную систему нужен номер без дефисов |
| 14 | Правила разбора вынесены из кода в шаблоны производителей, добавлено определение модели по номеру детали | Форматы идентификаторов у производителей разные; текст модели на шильдике часто мелкий, в тени или у края наклейки и не читается, тогда как номер детали приходит со штрихкода |
